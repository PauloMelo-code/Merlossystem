# Catálogo de requisitos — IDs estáveis, cor se faltar, como verificar

Cada ID é citado no relatório e comparado entre execuções. **Não renumere.** Requisito novo entra
no fim do domínio (ex.: `A7`), nunca no meio.

## A sinaleira

| Cor | Definição operacional |
| :--- | :--- |
| 🔴 **Crítico** | Permite tomar conta, escalar para dono, entrar sem credencial, ou impede saber que isso aconteceu. Bloqueia entrega. |
| 🟠 **Alto** | Reduz uma barreira a quase nada em cenário realista (credencial vazada, cookie roubado, e-mail comprometido); controle fundamental ausente com contorno parcial. |
| 🟡 **Médio** | Enfraquece defesa em profundidade ou depende de premissa não garantida (plataforma, disciplina). |
| 🟢 **Baixo** | Higiene, observabilidade, postura. |
| ⚪ **N/A ou não verificável** | Componente inexistente **ou** evidência não obtida — o relatório diz qual. |

Regra de ajuste: a cor da tabela é o padrão. Subir ou descer exige **uma frase de justificativa**
no achado (ex.: "🟠→🟡 porque a plataforma sobrescreve `x-forwarded-for`, medido em X").

Normas citadas: **NIST** = SP 800-63B-4 (jul/2025); **ASVS** = OWASP ASVS 5.0.0 (mai/2025);
**A07** = OWASP Top 10:2025 A07. Detalhe em `standards-and-recency.md`.

## A — Inventário e isonomia de caminhos

| ID | Requisito | Falta | Como verificar | Norma |
| :--- | :--- | :---: | :--- | :--- |
| **A1** | Inventário escrito de TODOS os caminhos que criam sessão/concedem acesso (humano, máquina, webhook, callback, plugin) | 🟠 | procurar doc/teste que enumera; conferir contra o roteador **em runtime** (Express: `router.stack`; Next: `find app -name route.ts` + `'use server'`; Django: `show_urls`; Rails: `rails routes`; Spring: `RequestMappingHandlerMapping`) | ASVS 6.1.3 |
| **A2** | Todo endpoint que a biblioteca/plugin **instala** está em uso, **desligado no servidor**, ou justificado | 🔴 | listar rotas do pacote instalado (ler `node_modules/<lib>/dist/**/routes*`, `urls.py`, `routes.rb`, filtros) × `grep` de chamadores no projeto; testar os sem chamador: devem responder 404/403 **no servidor** | ASVS 6.3.4 |
| **A3** | Zero rotas/ações de escrita sem guarda, provado por varredura por **identidade de função** | 🔴 | passada 1: vocabulário de guardas (`grep -ohE "\b\w*(Auth|Guard|Permission|Protect|require\w*)\w*\b"` no roteador); passada 2: inverter. Server Actions: todo export de módulo `'use server'` começa por guarda? Nunca usar `fn.name` (arrow anônima mente) | A07 |
| **A4** | Autenticação de **máquina** é canal separado do login humano; recusa cruzada com códigos distintos | 🟠 | dois módulos/middlewares; testar: API key no login humano → 403 próprio; conta humana no canal de máquina → 403 próprio | ASVS 6.3.4 |
| **A5** | A **borda** (middleware/`proxy.ts`, API gateway, ingress, service mesh, WAF, CDN) **não é** a única barreira: cada página, handler, action ou serviço confere sessão/identidade **por conta própria** | 🔴 | `grep` das rotas protegidas pela chamada ao portão; chamar o serviço/rota **por dentro** da borda (porta interna, `kubectl port-forward`, URL direta do container) sem credencial → deve ser 401; *exemplo Next*: `x-middleware-subrequest` forjado e prefetch (`?_rsc`, `Next-Router-Prefetch`) contra rota protegida | A07 · CVE-2025-29927 |
| **A6** | Área pública: teto de volume por IP na **primeira linha** de cada escrita; tokens efêmeros hasheados e em fragmento; nenhuma escrita anônima sem teto | 🟠 | ler as funções públicas de escrita; a 1ª instrução é o limitador? Token de convite/status em `#`? | — |
| **A7** | Login social/OIDC/SAML: sistema como **cliente** do IdP (🔴 se aplicável). Identidade da conta = (`iss`, `sub`) — **nunca** só e-mail (spoofável via outro IdP); vínculo automático a conta existente só com `email_verified` do IdP; `state`+PKCE no code flow; `nonce` do ID Token conferido; `aud`==`client_id`; `iss` por igualdade exata (mix-up); assinatura do ID Token/asserção SAML validada (`alg: none` recusado), asserção SAML de uso único | 🔴 se aplicável | ler o callback: casa conta por (`iss`,`sub`) ou por `WHERE email =`? `grep -i email_verified` no vínculo; forjar `state`, `nonce`, `aud` de outro cliente, `iss` com sufixo, `code`/asserção reutilizado(a) → todos devem ser recusados | ASVS 6.8.1–6.8.3, 10.2.1, 10.2.2, 10.5.1, 10.5.2, 10.5.4 |
| **A8** | Superfícies de **endpoint único** (GraphQL, gRPC, tRPC/JSON-RPC): a guarda é por **resolver/método/procedure**, não por rota; **aliases e lote (batching)** na MESMA requisição contam para o limitador e o bloqueio por conta (C1/C2) por **operação**, não por requisição HTTP | 🔴 | listar resolvers/métodos (GraphQL: introspecção `{"query":"{__schema{mutationType{fields{name}}}}"}` em homologação; gRPC: `grpcurl -plaintext host:port list`; tRPC: ler o `appRouter`) × quem chama o guarda; mutação de login repetida 20× por alias na mesma requisição → deve bloquear na N-ésima operação, não contar 1 requisição | A07 |

## B — Senha

| ID | Requisito | Falta | Como verificar | Norma |
| :--- | :--- | :---: | :--- | :--- |
| **B1** | KDF lento com memória: **Argon2id** (≥ 19 MiB, t=2, p=1) ou **scrypt** (N ≥ 2¹⁷, r=8, p=1); bcrypt só legado (custo ≥ 10, ≤ 72 bytes); PBKDF2 só por exigência FIPS (≥ 600k iterações SHA-256) | 🔴 | config no código **e** classificação dos hashes no banco por regex (`$argon2id$`, `$2[aby]$`, `<hex>:<hex>` scrypt do Better Auth, `pbkdf2_`, `$P$` phpass; `^[0-9a-f]{32,128}$` sem sal = INSEGURO) | OWASP Password Storage |
| **B2** | Mínimo **≥ 15** se a senha é fator único; **≥ 8** só com 2º fator real; máximo **≥ 64** (teto por custo) | 🟠 | constante da política; confirmar que é aplicada nos caminhos que **gravam** | NIST 3.1.1.2 · ASVS 6.2.1, 6.2.9 |
| **B3** | Verificada contra lista de senhas vazadas/comuns (HIBP k-anonimato ou lista local ≥ top 3000), **fail-open com aviso** | 🟠 | chamada existe? Indisponibilidade bloqueia cadastro? (não deve); contar quantas entradas da lista têm ≥ 15 chars — igualdade exata some quando o mínimo do B2 é ≥ 15 (medido: ~0 no top de listas comuns), e o controle fica morto por construção; testar `Password123456!` e `Senha@Empresa2026` (contextual) como candidatas reais de cadastro | NIST 3.1.1.2 · ASVS 6.2.4, 6.2.12 |
| **B4** | Sem regras de composição obrigatórias; sem expiração periódica; troca forçada só por suspeita | 🟡 | regex de classe usada como **bloqueio**? cron de expiração? | NIST 3.1.1.2 · ASVS 6.2.5, 6.2.10 |
| **B5** | Paste e gerenciador permitidos; `type=password` com "mostrar"; senha verificada **exatamente** como recebida (NFC para hash é aceitável; `trim`/`toLowerCase`/truncar não) | 🟡 | `grep onPaste`, `maxlength` curto, `trim(` na senha | ASVS 6.2.6–6.2.8 |
| **B6** | Termos contextuais (nome, e-mail, marca) e sequências (alfabeto, teclado, repetição) reprovados **deterministicamente** no mesmo módulo que a tela usa | 🟡 | módulo único servidor+tela? teste de paridade — inclusive de mensagem: se o servidor devolve N motivos e a tela resume em 1 genérico, a paridade falhou; vetores mínimos: `Abcdefghij12345!` (comprimento não pode mascarar sequência), `abcabcabcab` (repetição não-divisível pelo período do padrão), `qwertyuiop12345` (teclado) | ASVS 6.1.2, 6.2.11 |
| **B7** | Histórico curto (≈5) conferido com o **mesmo KDF**; leitura **fail-closed** | 🟡 | tabela + função; o que acontece se a leitura falhar? | — |
| **B8** | Teto bruto de entrada conferido **antes** de normalizar/avaliar/hashear | 🟠 | 1ª linha do caminho lê `.length` cru? Testar POST com senha de 1 MB: deve cair em µs | — |
| **B9** | Política roda em **todo** caminho que grava (cadastro, reset, troca, set por admin) e em **nenhum** que só confere (login, verify-password, enable-2FA) | 🔴 | lista branca explícita; onde o hook está pendurado? (Better Auth: `hooks.before`, nunca `password.hash`) | — |
| **B10** | Troca de senha exige a **senha atual**; nova passa pela política inteira | 🔴 | endpoint pede `currentPassword`? | ASVS 6.2.3 |

## C — Login, anti-automação e oráculos

| ID | Requisito | Falta | Como verificar | Norma |
| :--- | :--- | :---: | :--- | :--- |
| **C1** | Bloqueio por **CONTA** após N falhas em janela deslizante, duração finita, **atômico** — uma única operação condicional do armazenamento, nunca ler-decidir-escrever | 🔴 | módulo + operação atômica (SQL: `UPDATE ... SET failed = failed+1, locked_until = CASE ...`; Mongo: `findOneAndUpdate` com `$inc`; Redis: `INCR`+`EXPIRE`/Lua; IdP hospedado: recurso nativo **ligado** — Keycloak Brute Force Detection, Auth0 Attack Protection, Entra Smart Lockout vêm **desligados por padrão**); 8 tentativas paralelas devem contar 8; framework sem lockout nativo (Django puro, Laravel, Passport, Flask-Login) exige módulo próprio — presença da lib não é evidência de que está ativo | OWASP Auth CS · NIST 3.2.2 |
| **C2** | Limitador por IP+rota com **armazenamento compartilhado** entre instâncias; **store indisponível é fail-open com alerta**, nunca 500 que barra login | 🟠 | `storage`/`store` do limitador; `Map`/memória em serverless = falha; derrubar o store (ou simular) → login **passa** e há alerta, não 500 | — |
| **C3** | Conta bloqueada/desativada recusada **antes do KDF** e **sem** contar nova falha | 🟠 | a guarda de conta roda antes do hash e curto-circuita o contador (Better Auth: `hooks.before` lança, `after` não roda; Django: `user_login_failed` não deve disparar p/ conta já bloqueada; Spring: `AccountStatusUserDetailsChecker` antes do `PasswordEncoder`); medir tempo — bloqueada deve responder em ms | — |
| **C4** | Toda recusa de login **byte-a-byte idêntica** (status, `code`, `message`, **ordem das chaves**) e com piso de tempo; KDF roda para e-mail inexistente | 🔴 | `curl -s -w '%{http_code} %{time_total}'` para: inexistente / senha errada / desativada / bloqueada / senha vencida — comparar corpo cru com `diff` | ASVS 6.3.8 · A07 |
| **C5** | Nenhuma **escrita** no banco disparada por requisição não autenticada sem teto | 🟠 | ler hooks `before` do login; `DELETE`/`UPDATE` ali? | — |
| **C6** | IP para limites/registros vem de **uma** função canônica que sabe se a plataforma sobrescreve `x-forwarded-for` | 🟠 | `grep "x-forwarded-for"` — mais de um lugar = achado; **medir** em homologação: XFF forjado grava qual IP? | — |
| **C7** | Vítima de bloqueio é avisada (e-mail, dedupe 24 h), **sem** alterar a resposta HTTP e **fora** do caminho da resposta (`void`, não `await`) | 🟡 | função de aviso; `await` no handler = oráculo de tempo | — |
| **C8** | Sem contas padrão; sem auto-cadastro aberto em sistema fechado (convite: token hasheado, uso único, expiração) | 🔴 | `disableSignUp`/guarda; `SELECT` de convites; testar `POST /sign-up` sem convite; testar login com a credencial padrão que o pacote/imagem de auth cria sozinho no primeiro boot (às vezes só documentada na instalação, às vezes só no log de subida — não assuma que não existe sem testar) | ASVS 6.3.2 |
| **C9** | Login por passkey **isento** do bloqueio por senha e **limpa** o contador (mitigador da negação de serviço por bloqueio) | 🟡 | guarda da passkey lê `locked_until`? (não deve) | — |
| **C10** | Cadastro com e-mail **não verificado** não recebe sessão nem permite vincular provedor social; verificar o e-mail (ou resetar a senha) **revoga sessões abertas** e **cancela troca de e-mail pendente** aberta antes da posse ser provada | 🔴 se há auto-cadastro ou login social | criar conta de teste com e-mail X sem verificar; guardar o cookie; verificar X por outro cliente → cookie antigo deve virar 401; pedir troca de e-mail e depois resetar a senha → a troca pendente deve ser cancelada; ler `accountLinking`/`trustedProviders` (aceita e-mail não verificado vindo do IdP social?) | ASVS 6.3 · Microsoft 2022 (pre-hijacking) |
| **C11** | Conclusão de auto-cadastro por convite casada por **chave pública** (documento, e-mail, telefone) **nunca sobrescreve** identidade existente: nome/documento nunca; contato só em coluna vazia; endereço só `INSERT`. Resposta **idêntica** casada/não-casada e devolve o **digitado**, nunca o valor do banco (senão o convite vira oráculo do dono da chave). Token de uso único **não sobrevive** a rollback de falha posterior na mesma transação | 🟠 | ler a action pública de conclusão de cadastro: há `UPDATE` incondicional sobre linha achada por documento/e-mail? o que volta pra tela? forçar erro de validação **depois** de consumir o token, em ambiente de teste: ele continua consumido? | ASVS 6.3.8 |

## D — Segundo fator e fatores fortes

| ID | Requisito | Falta | Como verificar | Norma |
| :--- | :--- | :---: | :--- | :--- |
| **D1** | Segundo passo **obrigatório para todo mundo**, ligado no provisionamento | 🔴 | `SELECT count(*) FILTER (WHERE NOT two_factor_enabled) FROM users WHERE is_active` deve ser 0 (ou equivalente: allauth `mfa_authenticator` sem linha, django-otp `otp_totp_totpdevice.confirmed=false`, Devise `otp_required_for_login=false`; em IdP externo não há banco local — conferir a política de MFA no provedor, ex. Auth0 Guardian, Cognito `MfaConfiguration`, Entra CA); caminho de cadastro/convite liga?; existe cookie/flag de dispositivo confiável (D15) que pule o passo? → D1 só é ✅ se D15 também for (ou não existir o recurso) | ASVS 6.3.3 |
| **D2** | Uma opção **resistente a phishing** (passkey/WebAuthn) oferecida e funcionando em produção | 🟠 | plugin registrado; `rpID` == hostname de produção; `GET /…/passkey/*` não é 404 em prod; admins têm chave cadastrada? | NIST 2.2 (AAL2 SHALL) |
| **D3** | Se o piso é **código por e-mail**, está escrito como **transição** (e-mail não é fator para o NIST; reset chega na mesma caixa) e há roteiro para TOTP/passkey | 🟡 | comentário/doc honesto; a tela chama de "MFA"? (não deve) | NIST 3.1.3.1 · ASVS 6.3.6 |
| **D4** | SMS/telefone **não** é fator nem canal de recuperação | 🟠 | `grep -i "sms\|twilio\|otp.*phone"` | NIST 3.1.3.3 |
| **D5** | OTP fora de banda (e-mail/SMS/push): **hasheado** em repouso; ≥ 6 dígitos CSPRNG (≥ 20 bits de entropia); validade **≤ 10 min**; uso único **atômico**; falha não estende validade; tentativas limitadas (NIST: teto de 100 por autenticador, 5–10 é o usual); comparação em **tempo constante** (`timingSafeEqual`/`hmac.compare_digest`/`hash_equals`), nunca `===`/`==` sobre o valor ou o hash; **nunca em log** | 🔴 | config (`storeOTP: hashed` ou equivalente; conferir a **unidade** da validade — minutos × segundos, ex.: `otpOptions.period` do Better Auth); `SELECT` da tabela de verificação após pedir código; `grep` do código nos loggers; medir `time_total` de 10 códigos errados com prefixo certo × 10 totalmente errados — diferença consistente denuncia comparação não constante | NIST 3.2.2 · ASVS 6.5.1, 6.5.4, 6.5.5 |
| **D6** | TOTP: semente **cifrada**; período 30 s; anti-replay do mesmo código; relógio do servidor | 🟠 | config; ler a semente no banco: é `otpauth`/base32 em claro? | ASVS 6.5.8 |
| **D7** | Códigos de resgate: CSPRNG; guardados **hasheados** com sal se curtos — cifra reversível **não** atende a norma (quem tem a chave lê todos; nunca ✅, no máximo 🟡 com justificativa); comparação em **tempo constante**; exibidos **uma vez**; uso único atômico; após o uso, emite código novo e avisa o dono (D12); tela mostra só **quantos restam** | 🔴 | ler a coluna no banco de teste (hash `$argon2id$`/scrypt × string curta reversível = cifra); action da tela devolve lista ou contagem? payload contém códigos? regenerar sem reautenticar (D11)? | NIST 3.1.2 · ASVS 6.5.2, 6.3.7 |
| **D8** | Passkey: servidor **exige `userVerified: true`** no cadastro e no login; cadastro exige **sessão fresca** | 🔴 | gancho pós-verificação confere UV? (Better Auth cabeia `requireUserVerification: false`); `requireSession`/`freshAge` | — |
| **D9** | Passkey contorna o código por e-mail **só** porque D8 vale; conta desativada recusada também por passkey | 🔴 | guarda de login confere `is_active`? | — |
| **D10** | **Desligar** o 2º fator, **ler semente TOTP**, **regenerar códigos**: se o ecossistema não oferece essa ação como recurso, endpoint não é alcançável por sessão+senha; se oferece **por desenho** (comum fora do Better Auth — Fortify, Keycloak, Ory, Clerk, Supabase, Auth0 expõem essa remoção como autoatendimento), o piso vira reautenticação forte e **fresca**, medida e não suposta pela doc; remover autenticador sempre **rotaciona** e **mantém** o piso (D1) | 🔴 | sondar `POST /two-factor/disable`, `/get-totp-uri`, `/generate-backup-codes` (e equivalentes do ecossistema em uso): sem chamador → 404 **sem corpo**; com chamador **por desenho** → medir a janela de reautenticação real na config instalada (ex.: Laravel Fortify `password_timeout`, Ory `privileged_session_max_age` — não supor pelo valor de exemplo da doc) e conferir aviso (D12) e trilha (L1); lista lida por ≥ 2 camadas | — |
| **D11** | Adicionar/substituir fator exige reautenticação **no nível (AAL) que a conta já tem hoje**: conta com TOTP/passkey ativo → **o fator existente é obrigatório**, não "ideal"; só a conta que tem **apenas senha** cadastra o primeiro fator com senha atual + sessão fresca | 🟠 | `/two-factor/enable` ou equivalente: pede o 2º fator já ativo, ou só senha? uma conta com passkey consegue reconfigurar 2FA usando só a senha? | NIST 4.1.2 (SHALL) · ASVS 7.5.1 |
| **D12** | **Aviso ao dono** por canal independente da transação a cada mudança de fator, senha, e-mail, telefone, códigos de resgate regenerados e recuperação concluída; o aviso traz **o que mudou, quando, e como contestar** (contato ou link para invalidar o autenticador recém-vinculado) | 🟠 | e-mails "senha alterada", "nova chave", "fator removido" existem? o texto traz contato/instrução de contestação, ou só avisa? | NIST 4.1.2 · ASVS 6.3.7 |
| **D13** | Falha de **entrega** do código produz registro CRITICAL + alerta (resposta ao cliente pode seguir genérica) | 🟠 | o `sendEmail` **retorna** erro ou lança? o chamador confere o retorno? | — |
| **D14** | Com passkey/TOTP cadastrado, a tela de login **não** oferece o fallback mais fraco (senha + código por e-mail/SMS) em pé de igualdade visual/funcional; caminho fraco fica atrás de "outras opções", com aviso | 🟠 | tela de login de uma conta com passkey/TOTP cadastrado: o botão do fallback tem o mesmo tamanho/destaque que o do fator forte? existe atalho de um clique sem aviso? | — |
| **D15** | "Lembrar este dispositivo" para pular o 2º fator (se existir) é **decisão escrita**, com prazo limitado (≤ 30 dias) — ou está **desligado**; o cookie de confiança é `HttpOnly`/`Secure`, **vinculado ao usuário e ao dispositivo** (nunca só ao IP, nunca válido para outra conta); troca de senha, remoção do fator e reset **derrubam** a confiança; dispositivos confiáveis ficam **visíveis e revogáveis** na tela de segurança; administradores **nunca** pulam o 2º fator | 🟠 | `grep -i "trustDevice\|remember.*device\|trusted_device"`; qual o prazo do cookie/token? ele sobrevive a troca/remoção de fator (D11) ou a reset (E3)? copiar o cookie para outro cliente/conta → deve exigir o 2º fator ou morrer no teto; a tela lista e revoga? | NIST 5.1 · OWASP MFA CS · ASVS 7.4.3 |
| **D16** | Domínio remetente dos e-mails de segurança (código do 2º fator, reset, avisos de D12) com **SPF**, **DKIM** e **DMARC** (`p=quarantine` ou `reject`) **alinhados**; template e remetente **separados** do transacional/marketing | 🟡 | `dig +short TXT <domínio>` e `dig +short TXT _dmarc.<domínio>`; ler o `From` de `sendResetPassword`/`sendOTP`; comparar com o remetente das notificações comerciais | NIST 3.1.3 (canal OOB) · OWASP Forgot Password CS |
| **D17** | Código/aprovação fora de banda **vinculado à requisição de autenticação que o gerou** (não vale para a anterior nem para a seguinte); reenvio gera código **novo** e invalida o antigo; push com limite de pedidos por conta/janela e **number matching** | 🟠 | pedir código, pedir de novo, usar o primeiro → deve ser recusado; código emitido no login A aceito no desafio da sessão B? (não deve); config do provedor de push (limite de pedidos, número a digitar) | ASVS 6.6.2, 6.6.4 · OWASP MFA CS |
| **D18** | Envio de OTP/reset/magic link tem **cooldown por conta-alvo** (≥ 30–60 s) além do teto por IP; reenvio invalida o código anterior (nunca dois válidos ao mesmo tempo); cooldown **não bloqueia o login** da vítima; sinal anti-bot (CAPTCHA acessível, PoW ou desafio de risco) avaliado em cadastro público e reset — decisão escrita | 🟠 | 5 pedidos de envio seguidos para a mesma conta em 10 s → a partir do 2º/3º a resposta segue **idêntica** (E1) mas o envio real cessa (checar mailhog/log); variar o IP a cada pedido → o cooldown por conta ainda vale; login da vítima continua funcionando | NIST 3.2.2 · OWASP Forgot Password CS |

## E — Recuperação de conta e troca de senha

| ID | Requisito | Falta | Como verificar | Norma |
| :--- | :--- | :---: | :--- | :--- |
| **E1** | Pedido de reset responde **sempre igual**; envio **fora** do caminho da resposta | 🔴 | `curl` inexistente × existente: corpo e `time_total` | ASVS 6.3.8 |
| **E2** | Token: ≥ 128 bits CSPRNG, **hasheado** no banco, uso único **atômico**, TTL ≤ 15–60 min, em **fragmento** ou POST (nunca `?token=`) | 🔴 | tabela de token do ecossistema (Better Auth: `SELECT identifier FROM verification`); link do e-mail; TTL config | — |
| **E3** | Reset **revoga todas as sessões**, zera bloqueio, **não cria sessão** | 🔴 | resposta do reset tem `Set-Cookie`? sessões do usuário após reset? | ASVS 6.4.3 |
